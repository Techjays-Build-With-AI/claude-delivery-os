Stage 01Install the plugin, wire the MCP servers

Two steps, both once per developer machine. First install from the Techjays marketplace so the /ba, /tl, /dev, /qa, /jetrix, /doc, and /delivery-os commands become available inside Claude Code. Then run /delivery-os:setup to point the plugin's MCP servers at your Jetrix environment.

Add the marketplace

/plugin marketplace add

Register the techjays-delivery-os marketplace with Claude Code. Runs once — the marketplace stays known until you remove it. All seven bundled plugins become installable after this.

/plugin marketplace add Techjays-Build-With-AI/claude-delivery-os

Install the plugins

/plugin install

Install delivery-os first — it carries the shared core every other plugin depends on. Then add whichever domain plugins the workspace needs; installing all seven is the common case for a full-flow machine.

/plugin install delivery-os@techjays-delivery-os
/plugin install jetrix@techjays-delivery-os
/plugin install ba@techjays-delivery-os
/plugin install tl@techjays-delivery-os
/plugin install dev@techjays-delivery-os
/plugin install qa@techjays-delivery-os
/plugin install doc@techjays-delivery-os
What each plugin brings
delivery-os
Shared core: workspace scaffold, document contract, canonical templates. Install first.
jetrix
/jetrix:init, /jetrix:pull, /jetrix:push, /jetrix:task-update — the sync layer between the workspace and Mission Control.
ba
/ba:scope, /ba:review, /ba:resolve, /ba:features — discovery to feature breakdown.
tl
/tl:plan, /tl:review, /tl:resolve, /tl:scaffold, /tl:code-map — technical context graph.
dev
/dev:plan, /dev:build, /dev:commit, /dev:fix-review, /dev:resolve, /dev:bootstrap — the delivery loop.
qa
/qa:audit, /qa:plan, /qa:setup, /qa:health — the test harness contract.
doc
/doc:proposal, /doc:deck, /doc:magic-board, /doc:workflow, /doc:walkthrough — client-facing artifacts in the Techjays house style.

Keep them fresh

/plugin marketplace update

Refresh the marketplace metadata — picks up plugins added or removed from techjays-delivery-os since you registered it. Run before a mass update if a new plugin was published.

/plugin marketplace update techjays-delivery-os

/plugin update

Pull the latest version of a specific plugin. Repeat per plugin, or pass --all to update every installed plugin from every registered marketplace.

/plugin update delivery-os@techjays-delivery-os
/plugin update --all
Order matters on updates. If delivery-os has a new shared-core version, update it first — the other plugins read its templates and vocabulary at load. A stale core against a fresh ba/tl/dev can throw contract errors.

Wire up the MCP servers

/delivery-os:setup

Register project-mcp, scope-mcp, task-mcp under their canonical short names. Triggers Claude Code's OAuth flow the first time.

/delivery-os:setup
Environment flags
 
Prod URLs (default when no flag is passed)
--staging
Point every MCP at staging URLs
--local
Point at localhost — only for MCP developers running the servers themselves
One environment per machine. To switch (e.g. prod → staging), claude mcp remove <name> for each server, then re-run /delivery-os:setup with the new flag. Idempotent — safe to re-run any time.

What each MCP handles

project-mcp

Reads Solution + app + env-config + repository-integration metadata from Jetrix. Used by /jetrix:init and every other Delivery OS flow to resolve identity.

scope-mcp

Pushes and pulls BA outputs (scope, registers, feature-index, shared-context) direct to Google Cloud Storage. File bytes never route through Claude's context.

task-mcp

Writes directly to Mission Control's Task & List APIs — feature Tasks, sub-tasks, Implementation tab bodies, status transitions, PR handoff.

Stage 02Bind the workspace to a Jetrix Solution

Every workspace binds to one Solution. This writes .jetrix/project.json (gitignored), pulls the connection map, and seeds the tree that BA, TL, QA, and Dev agents write into.

/jetrix:init

Bind to an existing Solution and scaffold the working tree in one shot. Accepts the Solution slug, ObjectId, or shows an interactive picker if no argument is passed.

/jetrix:init
/jetrix:init <solution-slug>
/jetrix:init <solution-object-id>
Flags
--skip-scaffold
Bind only; skip seeding .jetrix/ tree. Useful when re-binding a workspace that already has content.

/jetrix:project-setup

Onboard from zero — interactive Q&A creates a new Solution and apps, binds this workspace to it, and scaffolds the tree. Prints a portal handoff block for linking GitHub repos and setting env branches in Jetrix.

/jetrix:project-setup

/delivery-os:init

Re-seed the .jetrix/ tree without touching identity. Idempotent — never clobbers existing files. Runs automatically inside /jetrix:init; only call directly to re-seed after --skip-scaffold.

/delivery-os:init

Stage 03Discovery — scope, review, break into features

The BA agent turns client artifacts into a living scope document plus supporting registers, reviews it critically, folds client answers back in, and finally decomposes it into a folder-per-feature implementation-ready breakdown.

Register sources

/ba:scope add

Register a discovery source without copying or moving the original. Six usage modes are auto-detected (transcript, requirements doc, wireframe, etc.).

/ba:scope add "path/to/client-folder/"
/ba:scope add "meeting-transcript.md"
/ba:scope add "https://drive.google.com/…"

Build & refresh

/ba:scope

Build or update the living scope from every registered source. Incremental by default. Produces ba/scope.md plus registers under ba/registers/.

/ba:scope
/ba:scope --refresh
Flags
--refresh
Full re-processing instead of incremental — rare; use when a source changed materially.

Review & resolve

/ba:review

Score every feature from a paranoid BA perspective. Renders an interactive HTML dashboard under ba/reviews/ that surfaces gaps, weak assumptions, and open questions for the client.

/ba:review
/ba:review ba/scope.md

/ba:resolve

Fold client answers back into the scope. Point at the *-responses.md file exported from the review HTML; the agent judges each answer and closes the questions.

/ba:resolve ba/reviews/scope-review-<ts>-responses.md

Decompose into features

/ba:features

Break the approved scope into implementation-ready features — one folder per feature under features/<slug>/ holding feature.md, workflow.md, acceptance-criteria.md, business-rules.md, nfrs.md, test-scenarios.md, dependencies.md, open-questions.md, and status.md.

/ba:features
/ba:features features/<slug>

Sync up to Jetrix

/jetrix:push scope

Publish ba/*.md, shared-context/*.md, and feature-index.md to Jetrix. Direct-to-GCS — 100 files is as fast as 1.

/jetrix:push scope

/jetrix:push feature

Create the Mission Control Task hierarchy from your feature folders — one parent Task per feature, one Sub-task per repo when a feature is split.

/jetrix:push feature

Stage 04Technical context graph

The Tech Lead agent turns your repos into a linked context graph — pages, endpoints, entities, each captured as a markdown unit with a semantic index so Dev-time agents can find the right file without opening any other.

Brownfield — reverse-map existing repos

/tl:code-map

Detect stack → extract every page, endpoint, and database object → write the code-context tree inside each mapped repo at <repo>/context/code-context/. Auto-authors shared-context/coding-standards.md from detected lint config + stack defaults if missing.

/tl:code-map
/tl:code-map <repo-path>
Arguments
 
No arg — maps every repo declared in .jetrix/project.json
<repo-path>
Absolute path to a single repository to map
Output travels with the code. The context/code-context/ tree is written inside the mapped repo (not in .jetrix/) and is meant to be committed. It diffs when the code changes, and anyone who clones the repo gets it.

Stage 05Just-in-time feature planning

Reads the TL context graph, decides whether a feature needs sub-tasks (multi-repo → one per repo; single-repo → parent alone), composes each sub-task's Description & Implementation, creates them in Mission Control, and surfaces every plan-time decision that would need build-time input as a blocker.

Patch a single MC field

/jetrix:task-update

Surgical patch of one field on an existing Mission Control task — never re-composes description or implementation, changes exactly what you point at. Use it for status corrections, small metadata edits, or re-syncing after someone changed a field directly in MC.

/jetrix:task-update --1
/jetrix:task-update --3 --field=status --value=readyForDev
/jetrix:task-update --7 --field=description
Arguments
--<task-number>
MC task number (e.g. --1, --12). Required.
--field=<name>
Field to patch: status, description, implementation, tags, or any custom field. Interactive picker if omitted.
--value=<value>
New value. Interactive prompt if omitted.
Not a re-plan. If the description or implementation needs a real re-derivation from the feature folder, re-run /dev:plan <target> instead — that goes through the 4-stage compose. task-update is for one-field patches only.

What lands after /dev:plan runs

  1. Local implementation.md written per sub-task (8-section stack-agnostic frame — Build sequence, Impacted components, Operations, Stored data, User-facing surfaces, Touch points, Risks + rollback, Shared contract).
  2. Local description.md written per sub-task in user-story format (As a … I want … So that …).
  3. Mission Control parent Task + one Sub-task per repo created; every push verified byte-identical via SHA-256 read-back.
  4. Local state at PLANNED; MC status at readyForDev.
  5. Terminal summary shows every task's clickable MC URL and the read-back token per push.
Next stop → Build. Once a task is at PLANNED, run /dev:build <target>. That's the stage where code and tests actually get written — and it never commits or pushes. Commit and PR happen only in /dev:commit.

Stage 06Write the code — never the commit

Takes a task at PLANNED and produces working code + tests on a fresh feature branch. Runs the tests against real services, applies build-time security fixes, flips context units from designed to implemented, and stops. Zero commits, zero stages, zero pushes from this command — that's /dev:commit.

/dev:build

Run the 11-stage build loop on one sub-task, a whole feature, or a batch. Auto-invokes /qa:setup when a repo has no quality-gates.md yet.

/dev:bootstrap

Greenfield project-zero scaffold. Delegates to TL to create the initial application (repo skeleton + tooling + green base build + shared-context/). Run once before /dev:build on a brand-new solution.

/dev:bootstrap <app-name>

The 11 stages, in order

  1. Branch — feature/<slug>-<sub> off the configured base, fresh from remote.
  2. Harness check — if the repo has no qa/quality-gates.md, auto-invoke /qa:setup so tests can actually run.
  3. Implement — dev-stack-adaptive-implementation reads implementation.md's 8-section frame + code-context units and writes source, dynamic per detected stack.
  4. Write tests — unit + integration + E2E per the QA harness contract; mock/tier alignment enforced (mocked tests cannot claim integration or E2E tier).
  5. Start external services — Postgres, Redis, message broker, etc. brought up via docker-compose; env vars verified before Stage 6.
  6. Run tests for real — against those live services. Bearer-null and auth-alignment regexes run as hard-fail checks.
  7. Acceptance map — every AC from feature.md linked to the test that proves it; missing links halt.
  8. Security review — Critical-only findings at build time (High+Critical is deferred to commit).
  9. Auto-fix loop — bounded: one compose + one lint + one auto-fix; further failures halt to human.
  10. Context flip — touched units go origin: designed → implemented; the three layer indexes rebuild.
  11. local-runbook.md — how to run the feature locally (env vars, seed data, commands). Working tree ends here, no git write.
No commits, no stages, no pushes. The working tree at the end has your new files + tests; git status will show them unstaged. That's the correct state — hand off to /dev:commit.
Mock / tier alignment is a hard fail. Tests marked integration or e2e that patch the database, HTTP client, or auth verifier fail Stage 6 with mock-contradicts-tier. Real backend calls only for those tiers.

Stage 07Review, merge context, commit, push, PR

Takes a task at BUILT and lands it. Asks which base branch to merge into, pulls it locally, runs the full commit-time review (security + code + acceptance), semantically merges the context graph against that baseline, commits the working tree, pushes the branch, and raises the PR — falling back through a four-step ladder if gh is unavailable.

/dev:commit

Run the 10-stage commit loop. Every stage records its evidence to commit-run.md; Stage 8 refuses to push unless every prior stage's evidence block is present.

/dev:commit <target>
/dev:commit Subtask-4 --resume
/dev:commit Subtask-4 --structured
Behavior flags
--resume
Skip stages already recorded in commit-run.md; re-enter Stage 7 with resolved conflicts if halted there.
--structured
Multiple commits by concern (source / tests / context / docs). Default is one commit for the whole diff.
--force-context-merge=ours
Emergency only — every semantic-merge conflict resolves to the feature-branch value; the PR body flags the override.

/dev:fix-review

After a reviewer leaves feedback on the PR, fold their comments back through the relevant commit stages — runs the code fix, re-runs affected tests, re-generates the acceptance map if AC changed, then pushes an update commit.

/dev:fix-review --pr=<number>
/dev:fix-review --file=feedback.md

The 10 stages, in order

  1. Preconditions — local state BUILT, MC agentExecuting, working tree not empty.
  2. Base branch prompt + pull — interactive picker (main / develop / release/*), then git fetch <remote> <base>:refs/remotes/<remote>/<base>. Records base_remote_sha.
  3. Security review — Critical + High findings at commit time (build handled Critical-only).
  4. Code review — 7 dimensions × 4 severities via dev-stack-adaptive-code-review.
  5. Acceptance re-verify — last sub-task also runs a real E2E against the freshly built stack.
  6. Bounded fix loop — up to 3 rounds; each round re-runs tests. Exhausted → halt to human.
  7. Semantic context merge — tl-semantic-context-merge against the pulled baseline. Non-skippable: Stage 8 refuses to push unless the invocation block is written to commit-run.md, even for a zero-change no-op.
  8. Gather & commit (7.5) — stage the working tree, commit with generated message (or --structured multi-commit split).
  9. Push — git push -u <remote> <branch>, verify remote SHA matches local.
  10. Raise PR — four-step fallback ladder (below). MC status flips to devReview.

PR-creation fallback ladder

  1. gh pr create — happy path when the GitHub CLI is installed and authenticated.
  2. git credential fill — if gh is missing but the OS keychain has GitHub credentials, use them against the REST API directly.
  3. gh auth login --with-token — prompt with a paste-token flow if the keychain has nothing.
  4. Web URL fallback — print a https://github.com/<owner>/<repo>/compare/<base>...<branch> URL with title + body pre-filled; you open it and click Create pull request.
Semantic merge is not git merge. It walks unit-level fields per field-merge-rules.md so, for example, an endpoint's ## Auth block from your branch and the same block from the base branch don't line-clobber each other. Conflicts open dev/context-merge-conflicts.md for a checkbox resolution.

Stage 08Own the harness, not the tests

The QA agent makes a repo testable — frameworks, config, CI wiring, fixtures, coverage thresholds, E2E scaffold — and publishes qa/quality-gates.md, the machine-readable contract that /dev:build and /dev:commit read to know what "green" means. It never writes per-feature tests (dev does that on the harness) and never weakens tests to go green.

/qa:audit

Read-only assessment of the current harness. Scores unit, integration, E2E, coverage, lint, type-check, CI, fixtures, mocks, and contract-tests. Produces a gap report for human review — no writes.

/qa:audit
/qa:audit <repo-path>

/qa:plan

Turn approved audit recommendations into a test-setup plan + a draft quality-gates.md. Escalates strategy choices (framework, coverage floor, what counts as E2E-worthy) instead of guessing.

/qa:plan

/qa:setup

Implement the harness against the approved plan. Bounded implement → verify loop; every green run stamps quality-gates.md. This is the command that unblocks a repo for /dev:build.

/qa:setup

/qa:health

Re-check for drift. Re-runs the audit against the current harness, compares to the last stamped gate, and flags regressions (dropped coverage, broken CI, disabled tests, mocked-out integration).

/qa:health
/dev:build auto-invokes /qa:setup when it hits a repo without quality-gates.md. The two commands chain — you rarely call /qa:setup by hand outside greenfield.
