Get started

Everything ships as one marketplace. You add the marketplace once (from GitHub or a local folder), install the plugins, and you're ready. Each agent lives under its own command namespace, so you get exact commands like /ba:scope, /dev:build, and /qa:audit.

3 Register the MCP servers

The plugins talk to Jetrix and Mission Control through three MCP servers, always under their canonical short names — project-mcp, scope-mcp, task-mcp. One command registers all three. Run it once per machine; it is idempotent, so re-running is safe.

# production (default)
/delivery-os:setup

# or point at staging / a local stack instead
/delivery-os:setup --staging
/delivery-os:setup --local
One environment per machine. The three names map to whichever URLs the flag selects. To switch environments later, claude mcp remove <name> for each and re-run with the new flag. If a later command halts saying task-mcp isn’t registered, this is the command it wants.

How it works

Delivery OS is a relay. Each agent does its part and hands off to the next — not by passing a file around, but by writing to a shared workspace that the next agent reads. You bind that workspace once with /jetrix:init (which scaffolds it); from there the folders are the handoff. Below is who does what, who starts first, and how the baton passes — for a greenfield project (no code yet) and a brownfield one (an existing codebase).

The cast — five roles, one workspace

Business Analyst /ba

Starts every project. Turns raw client material into a living scope, then breaks it into an implementation-ready feature set.

Technical Lead /tl

Turns features into a technical context graph (pages, endpoints, entities), reviews specs, and — on greenfield — scaffolds the initial repo.

Quality Assurance /qa

Makes the repo testable: stands up the test harness and publishes the quality-gate contract the Dev loop verifies against.

Developer /dev

Ships each feature through three commands — plan, build, commit — validating against the acceptance criteria and QA's gates, and stopping at a PR for human review.

Documentation /doc

Runs alongside — produces client-facing artifacts (proposal, workflow walkthrough, magic board) from the BA scope, mainly during discovery/sales.

The golden rule: an agent only reads another agent's published output, never its working notes. The BA writes ba/ and features/; the TL writes the code-context graph inside each repo at <repo>/context/code-context/; QA writes qa/quality-gates.md; Dev writes each feature's dev/ folder, the task files, and the PR summary. Because it's all in the workspace (and the repo), any agent — or teammate — can pick up where the last left off.
Centralizing to Jetrix? The same relay runs, but the workspace becomes a working copy of a central Jetrix project that is the source of truth. Bind once with /jetrix:init (or /jetrix:project-setup from zero), run /jetrix:pull scope before you work, and /jetrix:push to publish each agent's output back as structured records. See the Jetrix tab.

A Greenfield — a brand-new project with no code yet

Nobody has written a line of application code. The job is to go from client material all the way to built, validated features. The order matters because each step needs the previous one's output.

  1. Set up the workspace (once). Register the MCP servers on this machine with /delivery-os:setup, then bind the folder: /jetrix:init <solution> if the Jetrix Solution exists, or /jetrix:project-setup to create it from zero. Either way you end with a bound .jetrix/ and the folder tree every agent reads and writes within.
  2. BA scopes the work. The Business Analyst runs /ba:scope add "…PRDs, FRDs, meeting notes…" to build the living scope.md, then tightens it with the /ba:review → /ba:resolve loop. (The Doc agent can draft the client proposal from this scope in parallel.)
  3. BA breaks scope into features. /ba:features initiative=<name> decomposes the scope into one folder per feature under features/, each with acceptance criteria, business rules, NFRs, test scenarios, dependencies and open questions — and stamps them all with the initiative name. This is the handoff to the build team.
  4. TL stands up the repo. Because there's no codebase and the stack is an architecture decision, the Technical Lead runs /tl:scaffold (or the Dev agent routes there automatically via /dev:bootstrap). It asks for any undecided stack choice with a recommendation, then produces a real repo with a green base build.
  5. QA makes it testable. On the fresh repo, QA runs /qa:audit → /qa:plan → /qa:setup to stand up the test harness (frameworks, CI, coverage, e2e) and publish qa/quality-gates.md — the contract that defines what "verified" means here, and which /dev:build refuses to start without.
  6. TL plans the features. /tl:plan initiative=<name> maps each feature to its pages, endpoints, and entities in the technical context graph. (You can skip running this yourself — the Dev loop auto-plans a feature via the TL if it isn't planned.)
  7. Dev ships each feature through the three-command loop: /dev:plan decides and surfaces any blocker for you to resolve, /dev:build implements on an isolated branch and validates against the acceptance criteria and QA's gates, /dev:commit reviews, commits, pushes and opens the PR. It never merges. See the Delivery Loop tab.
  8. A human reviews and merges. Then Dev moves to the next feature. Repeat until the initiative is done.

You don't have to memorize the order. Every gate names the command that fixes it. No repo → /dev:bootstrap (TL scaffold); feature not in the context graph → /dev:plan auto-runs /tl:plan; no test harness → /qa:setup; no coding-standards.md → /tl:code-map or /tl:scaffold; open plan blockers → /dev:resolve --plan. Nothing guesses its way past a missing prerequisite.

B Brownfield — an existing codebase you're adding to

The app already exists and (often) some scope with it. You're adding an increment, usually with several developers working in parallel. Two steps from greenfield drop away — you don't scaffold a repo, and you don't re-scope what's already built — and the initiative becomes the tool that keeps each developer focused on their own batch.

  1. BA scopes only the increment. Run /ba:scope add "…just the new material…" to update the living scope, or point /ba:features straight at an existing scope document. Keeping the scope to the new work is the cleanest way to avoid regenerating features you've already shipped.
  2. BA breaks it down under a new initiative. /ba:features initiative=<new-batch> creates folders for just the new features and tags them. If your scope covers the whole system, mark already-shipped features Released in the index so only the new ones flow downstream. Each developer uses their own initiative name, so the shared features/ folder stays sortable.
  3. TL maps the existing code into a committed code-context tree. Run /tl:code-map repo=<path> once to reverse-engineer the repo — deriving every page, endpoint and database object already there, grouped by business domain, into <repo>/context/code-context/. This is the brownfield equivalent of greenfield's scaffold step: it gives the build team (and their agents) the technical context the code already embodies, so planning the new increment reuses it.
  4. QA checks the existing setup. /qa:audit on the real repo shows what testing already exists and where the gaps are; /qa:setup fills only what's missing and updates the quality-gate contract. (No need to start from scratch if a harness is already there.)
  5. TL plans just the new batch. /tl:plan initiative=<new-batch> plans only that developer's features, ignoring everyone else's in-flight work.
  6. Dev ships into the existing repo. /dev:plan initiative=<new-batch> → /dev:build → /dev:commit, per feature. There is no scaffolding step — the repo already exists, and /tl:code-map gave the loop the as-built context it needs. A feature touching several repos is split into one sub-task per repo automatically.
  7. Human reviews and merges, same as greenfield.

Multiple developers, one repo. Because features/ lives in the workspace, everyone's in-flight features share it. The initiative is what keeps a developer focused on their own batch: /ba:features stamps it, and /tl:plan, /dev:plan and /dev:build filter by it, so Dev B never trips over Dev A's four unfinished features. Pair it with per-initiative branches for clean merges.

The delivery loop

Everything upstream — the BA scope, the TL context graph, the QA harness — exists to make this loop safe to run. It is the per-feature cycle the Dev agent executes, and since v2.2 it is split across three explicit commands instead of one long /dev:build. The split exists so that every decision a human might need to make happens at plan time, every line of code is written at build time, and every irreversible git operation happens at commit time — never mixed together.

/dev:plan /dev:resolve /dev:build /dev:commit /dev:fix-review 
THE LOOP — per feature

  /dev:plan <task>      →  analysis · blockers · implementation.md · MC tasks
   │                        ends PLANNED  ·  or BLOCKED_ON_PLAN
   │
   ├─(blocked)─►  /dev:resolve --plan <task>   →  walk each PB-### → /dev:plan --resume
   │
  /dev:build <task>     →  branch · code · tests · acceptance map · security (Critical)
   │                        ends IN_PROGRESS  ·  working tree UNCOMMITTED
   │
  /dev:commit <task>    →  security (Critical+High) · code review · semantic merge
   │                        · commit · push · PR       ends REVIEW
   │
  HUMAN reviews the PR   →  /dev:fix-review for comments  →  merge (never the agent)
The one invariant worth memorizing. /dev:build never stages, commits, or pushes — every file it writes lands in the working tree and stays there. /dev:commit owns the entire git-write boundary: it gathers that working tree, structures the commit, pushes the branch, and opens the PR. If you see uncommitted changes after a build, that is the design working, not a failure.

1 Plan it — /dev:plan

Just-in-time planning for one task or many. It verifies the TL context graph is current (auto-running /tl:plan if it isn’t), decides whether the feature needs splitting across repos, analyses code-level impact, surfaces every decision a human still owes, and only then composes the plan and pushes it to Mission Control.

# one feature, by any identifier it can resolve
/dev:plan supplier-onboarding
/dev:plan Feature-4
/dev:plan FEAT-SUP-001

# or a whole batch, in parallel
/dev:plan list="Supplier Management"
/dev:plan initiative=payments-v2
/dev:plan --all --concurrency=5

# flags
/dev:plan <target> --split | --no-split    # force / forbid sub-task decomposition
/dev:plan <target> --dry-run               # compose locally, push nothing to MC
/dev:plan <target> --resume                # fold blocker resolutions, then re-compose

Its four stages

  1. Code-context readiness. Confirms the feature’s pages, endpoints and entities exist in the TL graph — auto-planning via tl-feature-planning if not — and checks the QA gate contract, offering to set it up or to infer tier pools from the detected stack.
  2. Per-task analysis. A dev-agent subagent runs readiness validation, a 12-dimension impact matrix (frontend, backend, database, authz, integrations, jobs, notifications, monitoring, tests, docs, flags, analytics) and an ordered build plan into a scratchpad — dev/analysis.md, or dev/<repo>-analysis.md per sub-task.
  3. Blocker detection. Scans five sources for decisions that would otherwise ambush the build. Anything found becomes a PB-### and halts this task — siblings carry on.
  4. Compose and push. tl-feature-compose reads the scratchpad plus the TL units and writes all eight sections of implementation.md in one pass, then upserts the task (and its sub-tasks) into Mission Control with a read-back verify.
Why analysis comes before compose (v2.3.1). In v2.2 the plan file was written early and appended to later, which meant a half-baked implementation.md could reach Mission Control. Now Stage 4 refuses to run unless the analysis scratchpad is complete and no blocker is open — so the plan is written once, whole.

Split or parent-alone

A feature touching several repos becomes one parent task plus one sub-task per repo; a single-repo feature, bug or story stays parent-alone. One consolidated [Y/n] checkpoint confirms the split for the whole batch before anything reaches MC.

Failure isolation

Features run in parallel up to --concurrency (default 5). One feature blocking or failing never halts the batch — the summary reports each outcome separately.

Read-back verified

Every push to Mission Control is verified by SHA-256 against what the server actually stored. A mismatch is retried once, then surfaced loudly — silent content loss is not possible.

Every run is journalled

dev/plan-run.md logs each stage’s skill invocations with inputs, outputs and duration. cat it to see exactly which skill fired and what it produced.

2 Unblock it — /dev:resolve --plan

A plan blocker (PB-###) is a decision the agent refuses to make for you: an undecided auth model, a missing integration contract, an ambiguous schema, an unresolved business-rule edge case. Stage 3 detects them from five sources — tl-plan.md [HELD] markers, BA open-questions.md rows marked “Blocks build”, unresolved integrations.md entries, system-landscape.md gaps, and unknown / TBD entries in the analysis — and parks the task at BLOCKED_ON_PLAN.

# walk every open blocker interactively, then fold + re-compose automatically
/dev:resolve --plan Feature-7

# blank target = pick the task that has open blockers
/dev:resolve --plan

For each blocker it shows the question with a real-world example, the options table with the TL’s recommendation, and a preview of what each option would mean. You pick an option, type free text, or skip. It writes your Resolution: to disk, then invokes /dev:plan --resume, which folds every resolution into the analysis deterministically per category, logs each as a DEC-###, and moves the task to PLANNED.

It never invents a resolution. Every Resolution: field is an option you picked, text you typed, or an explicit skip that leaves the task blocked. You can also edit dev/plan-blockers.md by hand and run /dev:plan --resume yourself — the interactive command just saves you the round trip.

Eleven stages, no prompts. /dev:build runs on a decidable plan or refuses — it will not ask you a question mid-run, because anything you could reasonably be asked was already resolved at plan time.

/dev:build supplier-onboarding

# or build exactly one sub-task

Adaptive to your stack

dev-stack-adaptive-implementation detects the stack, infers the repo’s own conventions from its existing code, and writes idiomatic changes with behavioural tests — rather than imposing one house pattern on every repo.

Mocks don’t count as integration

A test that mocks HTTP, the database, or auth middleware is a unit test, whatever the file is called. Claiming it as integration or e2e is a false coverage claim and halts the build. Integration tiers require the real service to actually start and pass a health probe.

Acceptance is the definition of done

Completion is a filled dev/acceptance-map.md — every criterion tied to a validation method and an evidence artifact, with a mocked flag per entry. A green test run alone is not enough.

Parallel across sub-tasks

Pointing at a split parent spawns one worker per sub-task — each with its own repo, branch and stage journal. One worker halting never stops its siblings. Safe because the wire contract is locked in the plan’s Shared contract section.

The two-gate security model

The same security-review skill runs twice at two different thresholds. Build-time blocks only on Critical, so a Medium finding doesn’t stall you mid-implementation. Commit-time blocks on Critical and High, because that is the last gate before code leaves your machine.

GateRuns atBlocks onLower findings
Build-time/dev:build Stage 9CriticalRecorded, carried forward
Commit-time/dev:commit Stage 3Critical + HighSurfaced in the PR body
Stages that cannot be reasoned away (v2.3.25 / v2.3.27). Two classes of gap turned up in real runs: an agent deciding the semantic context merge “would be a no-op” and skipping it, and an agent seeing review findings and fixing them inline instead of running the fix loop. Both are now mandatory and verifiable: the stage must invoke its skill and record a real invocation trace in commit-run.md, and Stage 8 refuses to push without it. A zero-change result is a legitimate outcome; skipping the invocation is not.

You pick the base branch

Stage 2 asks which branch the PR merges into, defaulting to the app’s env_branches.dev and marking it recommended — no more silent defaulting to a stale value. main, master and production are refused without an explicit override.

Secrets never get staged

Stage 7.5 greps the stage-worthy set for .env*, credential, secret, token, .pem and .key patterns and halts for human review if any match — it will not quietly add them to a gitignore.

No gh? Still fine

PR creation walks a four-step ladder: the gh CLI, then the PAT already in your Git credential manager, then a stored gh token, and finally a pre-filled compare URL you click. gh is no longer a hard dependency.

LangChain — Eval Engineering

What it is. An approach (and skill) from LangChain for building the tests that measure an AI agent. Rather than eyeballing whether an LLM feature "seems right," it produces executable evals — each pairing an instruction (the task), an environment (the tools and data it runs against), and a verifier (a scorer that decides pass/fail). It inspects the codebase and, where available, real production traces to find where an agent fails, turns each failure into an eval, and runs a tight mine → build an eval → improve the agent → rerun loop. A constant theme is guarding against reward hacking — the agent satisfying the verifier without doing the work (claiming an action it never took, over-citing irrelevant sources, exploiting exposed answers). Read the write-up: langchain.com/blog/towards-automating-eval-engineering.

Why we leverage it. Our TL /tl:review already scores an Evaluation strategy area for applied-AI specs — but scoring a plan is not the same as producing runnable verifiers. LangChain's eval-engineering method is that missing piece: it turns "this feature uses an LLM" into concrete, rerunnable evidence of whether the behaviour is correct. So rather than write our own eval methodology from scratch, we adopt theirs into the two agents that plan and build.

How Delivery OS uses it — TL designs, Dev runs, QA is the infra

TL — plan the evals /tl:plan

For a feature with an LLM/AI component, feature planning adds an eval layer to the technical context graph: for each AI-driven acceptance criterion it designs an eval unit (instruction · environment · verifier), decides which tool calls run live vs. simulated (paid or prod-writing calls get simulated), flags reward-hacking risks, and logs the design as a DEC-###.

Dev — run & inspect /dev:build

In the delivery loop's TESTING phase the dev agent materializes those evals into runnable verifiers, runs them as first-class checks feeding the acceptance map, and inspects both sides — the agent's trajectory and the verifier's result — to catch shortcuts before calling a criterion passed. Failures iterate through the existing bounded repair loop.

QA — the harness /qa:setup

QA still owns the test infrastructure and the quality-gates.md contract. Evals plug into it as another gate type — TL designs the eval, Dev runs it, QA's harness is what it runs on. No agent's ownership changes.

Our adoption is hybrid and scoped. We adapt the method natively so it's stack-agnostic and needs no LangSmith or Docker to work — with an optional Harbor / LangSmith export for teams that do run that stack (trace mining via langsmith-cli, Harbor task output). And it's gated to applied-AI / LLM features: deterministic CRUD features keep the normal acceptance-map flow, so we only pay the eval-engineering cost where non-deterministic behaviour actually needs it.
Status: adopting. Eval-engineering is being folded into tl-feature-planning and feature-delivery-loop now — it applies to AI/LLM features and layers on top of today's flow without changing how non-AI features are planned or built. The Evaluation strategy scoring in /tl:review is already live.

The working-copy model

You pull the slices you need into a local cache, do a whole piece of work locally (fast, reviewable, no round-trip per read, works offline), and when you're satisfied you push it back. A push is a deliberate commit, not an autosave — nothing local is published until you push.

  1. Bind once. /jetrix:init <project-slug> records which Jetrix project this workspace maps to in the committed .jetrix/project.json and scaffolds an empty, gitignored .jetrix/cache/. It fetches no content — binding stays fast.
  2. Pull. /jetrix:pull <stage> fills the cache from Jetrix. The stage picks what to refresh — scope (BA outputs, feature folders and the connection map in one go), connection-map, task / sprint / list for a single feature or a set, or all. It is incremental: a per-file content hash means anything unchanged is skipped without downloading, and files stream straight from storage in parallel, so a large pull is not much slower than a small one.
  3. Work locally. The BA, TL, and Dev agents read and write the cache like any workspace.
  4. Push. /jetrix:push <stage> publishes your changes back as structured records (requirements, workflows, features, endpoints, …), not a document blob. Stages: scope, feature, task, implementation, context, deliverable. It is idempotent (upsert by stable id, so re-pushing updates instead of duplicating), transactional (propose → preview a diff → commit), and safe (pull-before-push; on a both-sides-changed conflict it stops rather than clobber a Jetrix edit). File bytes stream from disk straight to storage, so a hundred-file push costs no more context than a one-file push.

What the review does

Bounds every feature

Enumerates the categories/buckets, the definitions used to classify them, what's covered vs excluded, and mandatory vs optional fields.

Scores coverage /10

Judges nine business dimensions (in/out scope, business rules, info & data, exceptions, acceptance, …) per feature.

Validates examples

Checks each feature against the client's shared examples: Pass / Partial / Conflict / No-examples.

Business, not technical

Judges what the business wants; leaves schema, APIs, and system design to the TL review.

Creates the feature/FEAT-… branch, edits code, and runs lint/type/test/build in the shell against the real repo — starting real services, not mocks, for anything above unit tier.

Acceptance = done

Completion is a filled acceptance map — every criterion tied to a validation method, an evidence artifact and a mocked flag. A green unit run alone is not enough.

Bounded repair loop

3 focused fixes per failure, 2 broad validation cycles — then it escalates instead of retrying blindly. When findings surface, running the repair loop is mandatory and its invocation is recorded; fixing inline and moving on is a spec violation.

Escalates, never guesses

Evals for AI features Adopting — when a feature has an LLM/AI component, the loop also runs and inspects the evals the TL designed (LangChain’s eval-engineering method) as part of validation, guarding against an agent that satisfies a check without doing the work. Deterministic features are unaffected. See the Leveraged Skills tab.

Commit, push, open the PR — /dev:commit

Ten stages, stricter than build at every overlapping gate: security at Critical and High, a seven-dimension adaptive code review, an acceptance re-verification with regression checking, a bounded fix loop, then the unit-level semantic merge of the code-context graph against the base branch. Only then does it gather the working tree, commit, push and raise the PR.

/dev:commit <target> --resume --structured --allow-protected-base

You confirm the base

Stage 2 asks which branch the PR merges into — defaulting to the app’s configured dev branch and marking it recommended — then fetches it locally so the semantic merge has a real baseline. Protected branches refuse without an override.

Secrets halt the commit

Before staging anything it greps for .env*, credential, secret, token, .pem and .key patterns and stops for human review rather than quietly gitignoring them.

gh is optional

PR creation walks a four-step ladder — the gh CLI, the PAT already in your Git credential manager, a stored gh token, then a pre-filled compare URL you click.

Never marks it done

It leaves the task at REVIEW / devReview. Moving to done belongs to the PR-merge webhook — the agent does not merge, deploy or force-push.

QA Agent — /qa

The Quality Assurance agent makes a repository properly testable and defines, in a machine-readable contract, exactly what "verified" means for it — so the Dev delivery loop validates features against a real, agreed bar instead of whatever tooling happens to exist. It audits the current test setup, recommends what's missing for you to approve, stands up the harness, proves it green, and publishes the quality-gate contract the Dev loop reads.

Commands

/qa:audit /qa:plan /qa:setup /qa:health
The one boundary that defines it: QA owns the test harness and strategy — frameworks, config, CI wiring, coverage thresholds, the e2e harness (e.g. Playwright config + a page-object/fixtures skeleton), test-data factories, mocking, conventions, and the quality-gate contract. The Dev agent writes the per-feature tests inside that harness, and /dev:build runs them. QA builds the kitchen; Dev cooks each dish. QA never writes a feature's tests and never weakens a check to go green.

Audit the setup — /qa:audit

Read-only. Point it at a repo (or use the current workspace). It detects the stack and scores the test setup across 12 areas — unit, integration, e2e, coverage, lint, format, type-check, CI, fixtures, mocking, contract testing, conventions — recording every gap as a stable QAF-### finding with a severity and a recommended fix. It changes nothing in the repo.

# assess an existing repo
/qa:audit repo=D:\acme\supplier-platform

# or the current workspace
/qa:audit

Scores 12 areas /10

Verdict bands: Not testable → Major gaps → Workable → Solid. Any Blocker caps it.

A decision surface

Each QAF-### recommendation carries a recommended option; you approve, skip, or defer it — QA acts only on what you approve.

Output lands in qa/audits/test-audit-<timestamp>.{html, md, json} — open the .html for the interactive report. Set Adopt / Skip / Defer per recommendation, then Export approvals.

Plan the setup — /qa:plan

Feed it the approvals file exported from the report. It reloads the audit, plans only the recommendations you approved, and drafts the quality-gate contract.

/qa:plan qa/audits/test-audit-<timestamp>-approvals.md

Writes qa/test-setup-plan.md (ordered steps, tools, CI changes, thresholds) plus a draft qa/quality-gates.md.

Build the harness — /qa:setup

Implements the plan in an isolated branch: installs and configures frameworks, wires CI, adds fixtures/mocks and coverage thresholds, scaffolds the e2e harness, writes the testing conventions — and proves a green smoke run. Then it finalizes the quality-gate contract.

/qa:setup
Never green-by-weakening. QA may not disable, skip, delete, or loosen a check or threshold to pass — that's an escalation with the trade-off named. Retry limits mirror the Dev loop (3 focused fixes per failing step, 2 broad smoke re-runs, 0 strategy guesses), and it never merges or deploys — the setup branch is handed off for human review.

Keep it honest — /qa:health

Re-runs the Required gates against the current repo to catch drift — a disabled check, a dropped coverage floor, a broken e2e config — and reports the deltas. It won't "repair" by lowering a gate; a threshold change is a human DEC-###.

/qa:health

The flow

/qa:audit   → scored gap report (HTML + MD + JSON)
   ↓  you review, set Adopt/Skip/Defer, export approvals
/qa:plan    → test-setup-plan.md + draft quality-gates.md
   ↓  you review the plan
/qa:setup   → build the harness in a branch → prove a green smoke run
   ↓            → finalize quality-gates.md (harness_status: Active)
/qa:health  → re-check the live harness → report drift
How it plugs into the Dev loop: qa/quality-gates.md is the contract. The Dev readiness gate reads it to confirm a usable harness exists (and routes to /qa:audit → /qa:setup if not, the same way project-zero routes to /dev:bootstrap); /dev:build reads it to know which checks are Required, the exact command for each, and the bar (coverage floor, when e2e/contract tests are mandatory). So the Dev loop stops guessing the tooling and verifies against a standard you set. Full guide: plugins/qa/qa_readme.md.

TL Agent — /tl

The Technical Lead reviews a technical specification for an applied-AI system the way a seasoned TL would before a team commits to building it. It reads the whole document, scores each build-readiness area out of 10 with concrete findings and fixes, and closes findings through a resolution loop. It also plans features into a technical context graph and scaffolds the initial project repo.

Commands

/tl:plan /tl:review /tl:resolve /tl:scaffold /tl:code-map /tl:maturity

Plan features into the context graph — /tl:plan

The TL's authoring job — and the handoff the Dev agent builds from. It turns the BA feature breakdown into a technical context graph: each feature is mapped to the frontend pages, backend endpoints, and database entities it needs, and every unit is wired to its neighbours in both directions so a coding agent can land on any node and traverse the whole design. Its defining rule is reuse, not duplication — it checks the per-layer indexes before creating anything, so a shared endpoint or table is one file with many back-links, never a copy per feature.

# plan one feature
/tl:plan features/invoice-ingestion

# or plan a whole initiative (batch) at once
/tl:plan initiative=payments-v2

Three linked layers

Pages (PAGE-<AREA>-NN) → endpoints (EP-<AREA>-NN) → entities (ENT-<AREA>-NN), each a self-contained unit file under context/frontend|backend|database, wired forward and back.

Reuse over duplication

Matches pages by route, endpoints by METHOD + path, entities by object name against the three layer indexes — reuses and extends what exists instead of minting a duplicate.

Design authority, grounded

Defines request/response shapes and entity columns (the TL's job), but grounds each in the feature and BA registers, marks inferred design by confidence, and turns real unknowns into open questions.

Traceable & checked

Entities cite the BA DATA-###, integrations cite INT-###; material choices are logged as DEC-###; a link-integrity check flags any dangling link or orphan before it finishes.

Output: the <repo>/context/code-context/{frontend,backend,database} unit files plus their three layer indexes (page-index.md, endpoint-index.md, entity-index.md). Re-run it when a feature changes — it updates in place, preserves existing back-links, and never duplicates a shared unit.
You can skip running it by hand. /dev:build's planning gate auto-runs /tl:plan on a feature that isn't planned yet, so the graph is guaranteed before the dev loop implements against it. Run it yourself when you want to review the design before building. On brownfield, run /tl:code-map first so planning reuses the as-built units.
Eval-aware planning Adopting — for features with an LLM/AI component, /tl:plan also designs the evals that will later verify them, adopting LangChain's eval-engineering method (instruction · environment · verifier). The dev loop then runs them. See the Leveraged Skills tab.

Scaffold the project — /tl:scaffold

On a greenfield project there's no codebase yet — and the dev agent won't scaffold on a guessed stack, because the stack is an architecture decision. /tl:scaffold is where that decision is made and executed. Executes a confirmed stack

Follows what the architecture pins down; recommends-and-asks for the rest (framework, DB, hosting, layout). Never silently guesses a critical choice.

Green base build

Skeleton + lint/format/type/test/build tooling + one passing test, verified install → lint → type → test → build — the exact readiness item dev checks.

Onboard an existing codebase — /tl:code-map

The brownfield counterpart to /tl:plan. Where planning builds context forward from features, /tl:code-map builds it backward from the real code: it reads an existing repository and derives every page, endpoint and database object that is already there, and the links between them. The result is written into that repository at <repo>/context/code-context/ and committed with the code, so it travels with the repo and diffs in review. A workspace registry (tl/code-map-registry.md) points at each mapped repo, so a later /tl:plan reuses those as-built units instead of duplicating them.

Everything is grouped by business domain. Each endpoint gets one markdown file recording its request contract, its validation rules and where each is enforced (schema middleware, handler check, database constraint), its business logic as ordered steps, and a data-access table naming every database object it touches, the access mechanism (ORM, direct query, stored procedure, function, view) and whether it reads, writes or executes. Database objects are grouped on disk by kind — tables/ collections/ views/ procedures/ functions/ triggers/ — each with its structure and its business purpose.

# map an existing repo into the context graph
/tl:code-map repo=D:\acme\legacy-portal

# map just one layer, or a slice of a monorepo
/tl:code-map repo=D:\acme\legacy-portal layers=backend,database scope=services/billing

Derived from code, not invented

Pages from the router, endpoints from route handlers (with METHOD + path), objects from models, migrations and DDL — each unit cites the source file it was read from.

Honest confidence

Every inferred link is marked Confirmed (static route/query) through to Assumed (dynamic/opaque); genuinely unresolvable links become open questions, not fabrications.

Index-first, so agents don't walk folders

Each layer index pairs a semantic domain map — what kinds of operations and objects live in each domain, in prose — with a unit table whose one-line summaries mirror the unit files. Root index → domain map → one file: three cheap reads instead of a directory crawl.

It also authors shared-context/coding-standards.md when the repo has none. That file is a hard prerequisite for /dev:build — the implementation skill checks every function it writes against its complexity, duplication and anti-pattern budgets, and the code review enforces the same policy. Greenfield gets the file from /tl:scaffold; brownfield gets it here, derived from what the repo already does plus the stack’s own lint-ecosystem defaults, with every threshold logged as a DEC-###. If /dev:build halts with coding-standards-missing, this is the command that fixes it.
Read-only on the code. It's static analysis — it never modifies, refactors, or runs the repo, and it never authors BA features or product scope from the code (that stays the BA's). Units are stamped origin: reverse-mapped with the commit they were read at; when you later run /tl:plan, features link into these same units. It writes only the context/code-context/ tree and never commits — you review and commit it like any other change.
Brownfield onboarding, in order: /ba:scope (scope from your existing docs) → /ba:features initiative=<batch> → /tl:code-map repo=<path> (build the as-built graph once) → /qa:audit → /tl:plan initiative=<batch> (reuses the mapped units) → then the delivery loop per feature: /dev:plan → /dev:build → /dev:commit.

Score production maturity — /tl:maturity

A read-only maturity audit of a built project. Where /tl:review scores a design document and /qa:audit scores the test harness, /tl:maturity scores the running system's reality across four domains — Code Quality & Maintainability, Test Quality & Verifiability, Infrastructure & Operations, and Security — and answers "is this production-grade, and where's the risk?" It prefers the project's own enforced tooling as evidence (lint, coverage, SARIF), tags every finding evidenced or attested, and reports a maturity score plus a separate Audit Confidence so a high score built on little measurement can't hide.

# score the current workspace / repo
/tl:maturity

# point at a repo; require the QA baseline before scoring
/tl:maturity repo=D:\acme\orders-service strict-baseline
Reminds you to run /qa:audit first. In preflight it checks whether the mandatory QA baseline (enforced lint, coverage gate, dependency + secret scanning) is in place. If it isn't, it points you at /qa:audit → /qa:setup and, by default, still scores in degraded mode at reduced Audit Confidence (with strict-baseline it stops instead). It is read-only on the repo — it installs nothing, changes no code or tests, never fabricates a score it couldn't measure, and routes baseline gaps back to QA rather than fixing them itself.
Where it fits the three audits: /tl:review scores the spec (before build) · /qa:audit scores the test harness (loop-readiness) · /tl:maturity scores the built system (production-readiness), consuming both.
