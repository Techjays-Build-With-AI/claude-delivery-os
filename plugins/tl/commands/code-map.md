# /tl:code-map

You onboard an **existing codebase** into Delivery OS by deriving a **code-context tree that lives inside that repository** — every page, endpoint and database object, grouped by business domain, with semantic indexes that let an agent find the right file in three cheap reads. Delegate the work to the **`tl-agent`** subagent, which runs `tl-code-map` in its own context.

## 1. Parse arguments

`$ARGUMENTS` may contain:

- **`repo=`** — path to the product repository to map (default: the current workspace / project repo). Repeatable, or comma-separated, to map several repos in one run (e.g. a separate frontend and backend repo) — each gets its own in-repo tree and a row in the workspace registry.
- **`layers=`** — `frontend`, `backend`, `database`, comma-separated. Default: all three, minus any the repo clearly doesn't contain.
- **`scope=`** — a subpath/module, to map a slice of a large monorepo at a time.
- **`domains=`** — restrict the run to named business domains (`domains=billing,subscription`) once a first pass has established the domain decomposition. Useful for re-mapping one area after a change.
- **`refresh=`** — `full` (re-derive everything; default on a first run) or `changed` (reconcile only units whose source files changed since the `mapped_from_commit` recorded in the existing tree). `changed` is the fast path for a re-run.

If there's no resolvable repository, say so and ask the user to point you at one — there's nothing to map without code.

**Where output goes** — state this back to the user before starting, because it writes inside their repo: the tree is created at **`<repo>/context/code-context/`** — a `context/` folder at the repo root, with `code-context/` inside it, created if the repo has none — intended to be **committed with the code**. If the repo already has a root-level `context/` used by the application, say so and confirm the location with the user before writing rather than mixing tool output into source. Running from a parent workspace over several repos still writes each repo's context into that repo. The only workspace-level file is the registry, `<workspace>/.jetrix/<project-name>/tl/code-map-registry.md`. Nothing else in the repository is touched, and nothing is committed — the user reviews and commits.

## 2. Delegate

Invoke the **tl-agent** subagent. Pass it this instruction:

> Reverse-map the repository at `<repo>` into a committed, index-first code-context tree using the `tl-code-map` skill — follow `references/extraction-guide.md` for how to read each layer, and write the exact files defined in `references/code-context-templates.md`. **Write the tree inside the mapped repository at `<repo>/context/code-context/`** (create the repo's `context/` folder if absent) — not into the workspace and never inside `.jetrix/`, which is gitignored — so it is committed with the code and travels with the repo; the only workspace-level artifact is `<workspace>/.jetrix/<project-name>/tl/code-map-registry.md`. Run it in **three passes**. **Pass A (discovery):** detect the stack (`shared-context/technology-stack.md` if present, else infer); **derive the business domains** using the extraction guide's ladder (module/folder → route prefix → naming → FK clusters) and assign `<AREA>` tokens, reusing tokens already in the registry so IDs never collide across repos; write a per-layer `_overview.md`; load any existing `code-context/` and the registry so you **reconcile, don't duplicate**; then **enumerate every unit from the declarative sources** — an OpenAPI/route manifest for endpoints, the router config for pages, the schema/migration state for database objects **of every kind** (tables, collections, views, stored procedures, functions, triggers) — into `code-context/map-coverage.md`, every row `pending`. **Pass B (detail):** burn the manifest down. **Database objects first**, one file per object in its kind folder (`tables/`, `collections/`, `views/`, `procedures/`, `functions/`, `triggers/`), each with its real structure **and its Business Purpose** — why the business has it, not just its DDL. **Endpoints next**, one file per `METHOD + path` (plus jobs/events/webhooks with their trigger), each recording the **Request** contract, the **Validation** rules *and where each is enforced* (schema middleware / handler check / database constraint), the **Business Logic** as ordered steps, and a **Data Access** table naming every object touched, its kind, the **access mechanism** (ORM · direct query · stored procedure · function · view · repository · cache) and read/write/execute. **Pages next**, one per routed surface, traced through the API client to the endpoints it consumes. Wire every link **both ways** — including object-to-object (view → source tables, procedure → objects touched, trigger → table it fires on and procedure it calls) — with a per-link **confidence** from the shared five-value vocabulary (`Confirmed · Likely · Assumed · Conflicting · Needs Clarification`): `Confirmed` where the code shows it directly, `Likely` for a strong conventional inference, `Assumed` where it's computed or you couldn't follow it through, `Conflicting`/`Needs Clarification` + an open question where the code contradicts itself or is opaque; **never invent** a relationship the code doesn't support. Mint IDs (`PAGE-/EP-/ENT-<AREA>-NN`) on the **same match keys** forward planning uses (route, normalised `METHOD+path`, object name), and keep every `##` heading forward planning defines **verbatim** (`Reads / Writes Entities`, `Behaviour / Business Rules`, `Called by`, `Used by Endpoints`, `Used by Features` = `(as-built)` until a feature links, `Integrations`, `Permissions`, `Status`) — the enhancements are additive sections, never renames — so a later `/tl:plan` reuses and extends these units instead of duplicating them. **Pass C (synthesis):** write the **semantic indexes** — each layer index gets a `## Domain Map` (a few lines per domain: what it is, what kinds of operations/objects live in it, what it touches, when to look elsewhere) **plus** a `## Units` table whose `Summary` cell is copied verbatim from each unit's own `## Summary`; the database index groups by **business domain** in the Domain Map and by **kind** in the unit tables. Then the root `code-context-index.md`, the `README.md` stating the index-first read protocol, and the workspace registry row. Split a layer index into per-domain sub-indexes if it outgrows one pass (~150 rows / ~500 lines). Mark every unit `origin: reverse-mapped` with a `[code › <file>]` Source Reference and a `mapped_from_commit` stamp. Do **not** modify, refactor, run, or commit the repository, do **not** write secrets or customer data into a tree that will be committed, and do **not** author BA features or infer product scope from the code. Run the link-integrity check **including the coverage check (every row `mapped`, `skipped`-with-a-note, or `removed` — no `pending` left) and the index checks (every unit has a Summary, every index row mirrors it, every index has a Domain Map)**, and report any code you couldn't confidently map. Return where the tree was written, units mapped per layer and per database kind (created vs reconciled), coverage (enumerated vs mapped vs skipped), the confidence spread, the domains derived and their area tokens, index and registry deltas, and integrity findings.
>
> Repository: `<repo or current workspace>` · Layers: `<layers or all>` · Scope: `<scope or whole repo>` · Domains: `<domains or all>` · Refresh: `<full|changed>`

When several repos were requested, delegate **one subagent per repo** (they can run concurrently — each writes only into its own repo). Tell each of them explicitly: **do not write the workspace registry — return your registry row and any pending cross-repo links instead.** You then write the registry yourself from the merged rows, resolve the cross-repo page→endpoint links across the now-complete set, and leave genuinely unresolvable ones in the registry's *Pending cross-repo links* table before reporting.

## 3. Surface the result

Present the **map summary**:

- **Where it landed** — `<repo>/context/code-context/`, committed with the code; remind the user it's uncommitted and worth reviewing in a PR like any other change.
- **The domain decomposition** — the domains derived and their area tokens. Lead with this: it's the decision that shapes the whole tree, and the one the user is most likely to want to correct.
- **Units** per layer and, for the database, **per kind** (tables / collections / views / procedures / functions / triggers), created vs reconciled.
- **Coverage** from `code-context/map-coverage.md` — enumerated vs mapped vs skipped.
- **Confidence spread** — the split across `Confirmed · Likely · Assumed · Conflicting · Needs Clarification`. Lead with the low-confidence areas if a meaningful share is below `Likely`.
- **Integrity findings** and any code that couldn't be confidently mapped (dynamic routes, generated handlers, reflection).

Link to the root index, the three layer indexes, the coverage manifest and the registry. Tell the user the as-built context is in place and how it's meant to be read — **index first**: root index → layer Domain Map → the one unit file — so they and their agents stop walking folders. Then the next steps for the brownfield increment: review and commit the tree, run `/qa:audit` on the repo to check testability, and `/tl:plan initiative=<batch>` for the new features, which will **reuse** these units rather than recreate them.
