# TL Code Map (existing repository → committed, index-first code context)

You turn a **codebase that already exists** into a **code-context tree that lives inside that repository** — a domain-organised, index-first description of every page, endpoint, and database object, and the links between them.

Two jobs, and the second is the one people underestimate:

1. **Derive the facts honestly.** Every unit points at the file it was read from and carries a confidence. Confidence uses the shared five-value vocabulary — `Confirmed · Likely · Assumed · Conflicting · Needs Clarification`. Where the code makes a relationship explicit (a route table, an ORM call, a `CALL sp_…`) it is `Confirmed`; a strong conventional inference is `Likely`; a computed URL, a string-built query or a generic repository you couldn't follow is `Assumed`; code that contradicts itself or is opaque is `Conflicting`/`Needs Clarification` and becomes an open question. You never fabricate a clean graph the code doesn't support.
2. **Make the result findable in three cheap reads.** The tree is written to be consumed by an agent with a limited context window. Indexes carry a **semantic Domain Map** — what kinds of things live in each domain, in prose — so a reader decides *which* files to open before opening any. That routing layer is the deliverable as much as the unit files are; an index that is only a table of file paths has failed at its job.

You read the repository; you change nothing in it except the `code-context/` tree you author.

## Operating contract

Read the **`delivery-os-conventions`** contract first if it isn't in context (frontmatter standard, stable IDs, controlled vocabulary). Your file schemas are in **`references/code-context-templates.md`** — the exact shape of every index, unit and manifest, and the index-first read protocol they exist to serve. Your extraction method — how to find each layer per stack, how to derive business domains, how to read validation and data access, how to mark confidence — is in **`references/extraction-guide.md`**. Read `tl-feature-planning`'s `references/planning-guide.md` for the reuse match keys, so a later `/tl:plan` reuses your units instead of duplicating them.

**Input:** the **product repository** (via `repo=<path>` or the current workspace) and, where present, `shared-context/{architecture.md, technology-stack.md}` for the confirmed stack.

**Output — and this is the important placement rule:** the tree is written **inside the mapped repository**, at `<repo>/context/code-context/` — a `context/` folder at the repo root, with `code-context/` inside it — and is **committed with the code**. Even when `/tl:code-map` runs from a parent workspace over several repos, each repo's context goes into that repo — never into the workspace, never inside `.jetrix/` (which is gitignored). The context then travels with the code: it is reviewable in a pull request, it diffs when the code changes, and anyone who clones the repo gets it. The only workspace-level artifact you write is **`<workspace>/.jetrix/<project-name>/tl/code-map-registry.md`** — a small pointer file listing each mapped repo, its context root, its indexes and its area tokens, so cross-repo links resolve and `/tl:plan` can find the as-built units.

```text
<repo>/context/code-context/          # create the repo's context/ folder if it has none
├── README.md · code-context-index.md · map-coverage.md
├── backend/   _overview.md · backend-index.md · domains/<domain>/endpoints/<slug>.md
├── frontend/  _overview.md · frontend-index.md · pages/<area>/<slug>.md
└── database/  _overview.md · database-index.md
              tables/ · collections/ · views/ · procedures/ · functions/ · triggers/
```

Create only the layers and kind-folders the repo actually has. Every reverse-mapped unit carries `origin: reverse-mapped`, `mapped_from`, `mapped_from_commit` and `map_confidence` in frontmatter, and a **code citation** (`[code › <relative/path>]`) in its Source References instead of a `FEAT-…` — at map time no feature is linked yet, so its `## Used by Features` section and index column read `(as-built)` until a later `/tl:plan` links one. Every `##` heading forward planning defines is kept **verbatim** (`Reads / Writes Entities`, `Behaviour / Business Rules`, `Called by`, `Used by Endpoints`, `Used by Features`, `Integrations`, `Permissions`, `Status`); your enhancements are additive sections, never renames. Reading git metadata (`git rev-parse HEAD`) for the commit stamp is a permitted read-only call; omit the field if it isn't available.

**Never write into `code-context/`:** secrets, connection strings, credentials, or customer data. It is a committed, shareable description of structure and intent — column names and types yes, sample values no.

## Workflow

Three passes. Discovery enumerates cheaply; detail writes one unit at a time; **synthesis** builds the semantic indexes from the units that were actually written. Enumeration order and link-resolution order are deliberately **decoupled** — enumerate whatever is cheapest first (routes and pages are declarative and list wholesale), but resolve cross-links only once all three layers are enumerated in `map-coverage.md`, so no page is ever written pointing at an endpoint file that doesn't exist yet.

### Pass A — Discovery (enumerate and orient; write no unit files)

1. **Detect the stack and layout.** Read `shared-context/technology-stack.md` if present, else infer from the repo — package manifests, framework config, folder conventions. Establish languages, frontend framework + router, backend framework + routing style, the ORM/data layer, and the database engine and migration tool. This decides *where* pages, endpoints and database objects live (see `references/extraction-guide.md`). Write a short per-layer **`_overview.md`** capturing that layer's stack, conventions and entry points, so every unit file below can stay lean and inherit shared context from one place.
2. **Derive the business domains.** Cluster the repo into domains (`account`, `billing`, `subscription`, `core`) using the ladder in the extraction guide — module/folder structure first, then route prefixes, then naming, then foreign-key clusters. Assign each domain an `<AREA>` token, **reusing tokens already in the registry** so IDs never collide across repos. The domain decomposition is the backbone of the whole tree: it determines the backend folders, the page areas, and how the database index groups. Log a `DEC-###` for any non-obvious grouping call.
3. **Load any existing context.** Read this repo's `code-context/` indexes if they exist, and the workspace registry, so you **reconcile, not duplicate** — a previous map run or a hand-authored graph is extended in place by match key.
4. **Enumerate every unit from the declarative sources.** Prefer an authoritative registry over hand-reading every file: an **OpenAPI/Swagger spec or route manifest** for endpoints, the **frontend router config** for pages, the **schema/migration state** for database objects. List every route (`METHOD + path`), every job/consumer/webhook with its trigger, every routed page, and every persisted object **of every kind** — tables, collections, views, procedures, functions, triggers — into **`code-context/map-coverage.md`**, every row `pending`, each with its source file and provisional domain. This manifest is the checklist Pass B burns down and the scope guard for a large app: it makes "what have we not looked at yet" explicit so nothing is silently missed.

### Pass B — Detail (write unit files, one at a time, off the manifest)

5. **Database objects first** — everything else references them. One file per object, in the folder for its **Kind**: `tables/`, `collections/`, `views/`, `procedures/`, `functions/`, `triggers/`. Give each its real structure (columns/keys for a table, document shape for a collection, definition and source objects for a view, signature and logic steps for a procedure or function, fire condition and effect for a trigger) **and its Business Purpose** — why the business has this object, which is the half a reader can't get from the DDL. Cite the migration/model file. Flip the manifest row to `mapped`.
6. **Endpoints next.** One file per operation as `METHOD + path`, plus jobs, event consumers and webhooks with their trigger. Read the handler through to its data layer and record four things the templates make first-class: the **Request** contract (path, query, body, headers), the **Validation** rules *and where each is enforced* (schema middleware, handler check, database constraint), the **Business Logic** as ordered steps, and the **Data Access** table — every object touched, its kind, the **access mechanism** (ORM, direct query, stored-procedure call, function, view, repository, cache) and whether it reads, writes or executes. A repo that computes money in a stored procedure and one that computes it in a service look identical in a "reads/writes entities" list and completely different here; that distinction is the point. Flip the row to `mapped`.
7. **Pages next.** One file per routed surface. Trace its API calls (service layer, `fetch`/`axios`, generated clients, query hooks, form actions) to the endpoints it consumes and wire `Consumes endpoints`. A modal, tab, drawer or widget is documented *inside* its page, not as its own unit. Flip the row to `mapped`.
8. **Wire every link both ways and set confidence.** page → endpoint → object, and back (`Called by`, `Used by`). Object-to-object links too: a view lists what it reads from, a procedure lists what it touches, a trigger lists the table it fires on and the procedure it calls — and each of those objects lists the caller back. Mark each link's confidence from how directly the code shows it. Where a link is genuinely unresolvable, record an open question on the unit rather than guessing. See `references/extraction-guide.md` §8 for when a language server is worth standing up to move links from `Assumed` to `Confirmed` — this is the pass it helps most.
9. **Mint IDs** append-only on the **same match keys** forward planning uses — route path for a page, normalised `METHOD + path` for an endpoint, object name for a database object — so `/tl:plan` reuses rather than duplicates. `PAGE-<AREA>-NN`, `EP-<AREA>-NN`, `ENT-<AREA>-NN` (all database kinds share the `ENT-` prefix; `Kind` distinguishes them).

### Pass C — Synthesis (build the retrieval layer)

10. **Write the semantic indexes.** For each layer, write the index in two parts: a **`## Domain Map`** — a few lines per domain saying what the domain *is*, what kinds of operations or objects live in it, what it touches, and when to look elsewhere — and a **`## Units`** table with one row per unit whose `Summary` cell is **copied verbatim** from that unit's own `## Summary` line, so the two can never drift. The database index carries both views: domains in the Domain Map, and the unit tables grouped by **kind**. Then write the root `code-context-index.md` (layers, domains, coverage, confidence) and the `README.md` stating the index-first read protocol. Synthesise the Domain Map **from the units you actually wrote** — it is a summary of evidence, never a guess about what a domain probably contains.
11. **Respect the index budget.** A layer index must stay readable in one pass. If its Units table passes ~150 rows or the file passes ~500 lines, keep the Domain Map and a roll-up in the layer index and split the per-unit rows into per-domain `<domain>-index.md` files. Never let an index degrade into a directory listing.
12. **Update the workspace registry** (`<workspace>/.jetrix/<project-name>/tl/code-map-registry.md`): this repo's path, layers, context root, commit, unit counts, index paths, area tokens, and any cross-repo link whose other end isn't mapped yet. **Single-repo run: write the file.** **Multi-repo run: do not write it** — concurrent mappers would clobber each other; **return** your registry row and pending-link rows to the caller, which merges them. This is what makes cross-repo links resolvable and as-built units reusable.
13. **Run the integrity check.** Every forward link has its back-link; every endpoint has a caller or a declared trigger; no orphan object (or it's marked reference/seed); every unit has a `## Summary` and every index row mirrors it; every index has a Domain Map; shared units appear once with multiple back-links; nothing duplicated. Plus the **coverage check**: every `map-coverage.md` row is `mapped`, `skipped`-with-a-note, or `removed` — no silent `pending`.
14. **Summarise in chat.** Units per layer and per kind (created vs reconciled), coverage (enumerated vs mapped vs skipped), the confidence spread, where the tree was written, integrity findings, and the next steps.

## Boundaries

You **author context from code; you do not**: modify, refactor, or run the repository — read-only static analysis, and the only files you create are the `code-context/` tree and the workspace registry (you do not commit them; the user decides when to commit); write BA features or infer product intent/scope from the code (features stay BA-owned — that is the deliberate boundary of this capability); invent a relationship, contract, validation rule or schema the code doesn't show (mark it `Assumed` or raise an open question); design *new* units (you record what exists — new design is `tl-feature-planning`); or write secrets or customer data into a tree that will be committed. Where the code is generated, dynamic, or opaque, a documented finding beats a confident fabrication. Log a `DEC-###` only for genuine interpretation calls (how you grouped domains, which area token you reused), not for facts read straight from the code.

## Return value

Return the headline: where the tree was written (`<repo>/context/code-context/`), units per layer and per database kind (created vs reconciled), the coverage from `map-coverage.md`, the confidence spread, the domains derived and their area tokens, the registry delta, link-integrity findings and any code you couldn't confidently map — and the next actions: review and commit the `code-context/` tree with the code, `/qa:audit` the repo for testability, and `/tl:plan initiative=<batch>` for new work, which will reuse this as-built context rather than recreate it.
