Install plugins & connect MCPs

One-time setup on your machine — install the marketplace, install the seven plugins, connect the four production MCPs to Claude Code, and bind your first workspace.

Steps

  1. Add the plugin marketplace

    Point Claude Code at the delivery-os marketplace repo. All seven plugins become installable.

    /plugin marketplace add <repo-url>
    ArgKindValue
    repo-urlrequiredgithub.com/Techjays-Build-With-AI/claude-delivery-os

  2. Install the seven plugins

    Install what your role needs. For a full end-to-end workflow, install all seven.

    /plugin install <plugin-name>
    ArgKindAccepted values
    plugin-namerequireddelivery-os-core · ba · tl · dev · qa · doc · jetrix

    Run once per plugin. To install all seven:

    /plugin install delivery-os-core
/plugin install ba
/plugin install tl
/plugin install dev
/plugin install qa
/plugin install doc
/plugin install jetrix
    Verify: /plugin list shows all seven under the delivery-os marketplace.

  3. Add each MCP to Claude Code

    In Claude Code, use the MCP command (or Settings → MCP) to add each of the four production URLs one at a time.

    /mcp add <name> <url>
    ArgKindNotes
    namerequiredLocal identifier — use the MCP's own name (project-mcp, etc.)
    urlrequiredProduction URL ending in /mcp
    /mcp add project-mcp  https://project-mcp-prod-423614975588.asia-south1.run.app/mcp
/mcp add scope-mcp    https://scope-mcp-prod-423614975588.asia-south1.run.app/mcp
/mcp add context-mcp  https://context-mcp-prod-423614975588.asia-south1.run.app/mcp
/mcp add task-mcp     https://task-mcp-prod-423614975588.asia-south1.run.app/mcp

    Alternatively, drop all four into .mcp.json or ~/.claude/config.json:

    {
  "mcpServers": {
    "project-mcp": { "type": "http", "url": "https://project-mcp-prod-423614975588.asia-south1.run.app/mcp" },
    "scope-mcp":   { "type": "http", "url": "https://scope-mcp-prod-423614975588.asia-south1.run.app/mcp" },
    "context-mcp": { "type": "http", "url": "https://context-mcp-prod-423614975588.asia-south1.run.app/mcp" },
    "task-mcp":    { "type": "http", "url": "https://task-mcp-prod-423614975588.asia-south1.run.app/mcp" }
  }
}

  4. Complete OAuth for each MCP

    On first use of any tool, Claude Code opens a Jetrix consent page in your browser. Sign in with your Jetrix account and approve. One handshake per MCP.

    First-time only: if you've never signed in to Mission Control, complete signup at your Jetrix instance first.

  5. Sanity check

    In a Claude conversation, ask:

    List my Jetrix solutions.

    Claude should call project_list_solutions via project-mcp and return your solutions. If four MCPs appear in your tool picker, wiring is complete.

Stage 01 · Init

Bind the workspace

Pick a Jetrix solution and set up the local Delivery OS workspace. Every workflow starts here — greenfield or brownfield.

No codebase yet. Fresh solution on Jetrix. You'll create the workspace from scratch.

  1. Create an empty folder and open Claude Code

    mkdir my-new-project && cd my-new-project
claude

  2. Run init

    /jetrix:init [solution=<slug|id>]
    ArgKindNotes
    solutionoptionalSolution slug or 24-hex ObjectId. Omit to pick interactively from the list.

    Claude lists your Jetrix solutions (via project-mcp). Pick the one you want to build.

  3. Init creates

    project.json, empty context/, ba-output/, shared-context/, dev-output/. Nothing else on disk.

Codebase exists. Workspace layers on top of the existing repo.

  1. Open the existing repo in Claude Code

    cd path/to/existing-repo
claude

  2. Run init

    /jetrix:init [solution=<slug|id>]
    ArgKindNotes
    solutionoptionalSame as greenfield — omit for interactive pick.

    Init detects the existing repo and won't overwrite it.

  3. Init creates alongside existing app code

    Same additions as greenfield. Your app code isn't touched.

    Confirm .gitignore is friendly to .jetrix/ and dev-output/ so local sync state doesn't leak into commits.
Stage 02 · Business Analyst

Scope & feature breakdown

Turn discovery inputs into a scored, feature-broken scope. Output: context/features/<slug>/ folders plus BA registers under ba-output/.

/ba:scope→ /ba:review→ /ba:resolve→ /ba:features→ /jetrix:push scope→ /jetrix:push feature

  1. Discover scope from client artifacts

    Drop discovery inputs (notes, docs, transcripts, mockups) into the workspace.

    /ba:scope
    ArgKindNotes
    —noneReads all discovery artifacts placed in the workspace root.

    Produces ba-output/scope.md, registers, glossary.

  2. Paranoid review

    /ba:review
    ArgKindNotes
    —noneScores every feature on coverage depth; flags gaps.

  3. Resolve blocking open questions

    /ba:resolve
    ArgKindNotes
    —noneIterates on OQs. Feed new info back until blockers clear.

  4. Break scope into features

    /ba:features [<slug>] [initiative=<name>]
    ArgKindNotes
    slugoptionalBreak down one feature only. Omit for all.
    initiativeoptionalStamp all created features with this initiative name.

    Produces context/features/<slug>/ with 8 files per feature.

  5. Push scope to Jetrix

    /jetrix:push scope
    ArgKindNotes
    —nonePushes ba-output/*, registers, shared-context/.

  6. Push features to Jetrix (as MC Tasks)

    /jetrix:push feature [<slug>]
    ArgKindNotes
    slugoptionalPush one feature. Omit for all changed features.
    Blocker-aware: features with unresolved Open+Blocks OQs or unavailable deps land as status: blocked. Resolve locally, re-push to clear.

Two sub-cases: (A) scope already on Jetrix — pull it. (B) new increment — run discovery for the new work only.

Case A — pull existing scope

/jetrix:pull scope
ArgKindNotes
—nonePulls scope + registers + all feature folders.

Skip to TL (Stage 03) once done.

Case B — delta discovery

  1. Run BA discovery for NEW work only

    /ba:scope
/ba:review
/ba:resolve

    Same args as greenfield. Registers get additive rows.

  2. Break new work into features

    /ba:features [<slug>] [initiative=<name>]

  3. Push the delta

    /jetrix:push scope
/jetrix:push feature
Stage 03 · Tech Lead

Plan the graph & compose the spec

Map every feature to real pages, endpoints, and entities. Compose a buildable per-feature technical brief the dev-agent consumes.

/tl:plan→ /tl:compose→ /jetrix:push context→ /jetrix:push implementation

  1. Plan the context graph

    /tl:plan <target> [initiative=<name>] [layers=frontend,backend,database]
    ArgKindNotes
    targetrequiredFeature folder, slug, FEAT-id, or context/features/ for all.
    initiativeoptionalRestrict planning to features stamped with this initiative.
    layersoptionalComma list. Default: all three layers.

    Creates unit files under context/frontend|backend|database/ plus the three indexes. Wires links both ways.

  2. Compose per-feature spec

    /tl:compose <target> [initiative=<name>] [--force]
    ArgKindNotes
    targetoptionalFeature folder, slug, or FEAT-id. Omit for all features.
    initiativeoptionalRestrict to features stamped with this initiative.
    --forceoptional flagRecompose even if graph inputs haven't changed since last compose.

    Writes context/features/<slug>/tl-plan.md. Role names only — no file paths in the doc.

  3. Push context graph

    /jetrix:push context [--env=dev|main]
    ArgKindNotes
    --envoptionalDefault dev. Use main only when pushing a baseline (paired with /tl:map --baseline).

  4. Push implementation to MC Tasks

    /jetrix:push implementation [<slug>]
    ArgKindNotes
    slugoptionalPush one feature's tl-plan.md. Omit for all with changed tl-plans.

    Each tl-plan.md lands verbatim in its MC Task's Implementation tab. Status flips to readyForDev — unless blockers exist, then blocked.

/tl:map→ /tl:map --baseline→ /jetrix:push context --env=main→ /tl:plan→ /tl:compose→ /jetrix:push implementation

  1. Reverse-map the existing codebase

    The brownfield-defining step. TL agent reads the repo and derives the graph. Every unit gets [code › <file>] citations.

    /tl:map [repo=<path>] [layers=frontend,backend,database] [scope=<subpath>]
    ArgKindNotes
    repooptionalPath to the product repo. Default: current workspace.
    layersoptionalComma list. Default: all three.
    scopeoptionalSubpath / module to map a slice of a monorepo at a time.
    Review low-confidence edges first. Every link is Confirmed or Assumed. Fix assumed ones before treating the graph as authoritative.

  2. Mark baseline and push to main env

    /tl:map --baseline
/jetrix:push context --env=main
    ArgKindNotes
    --baselineflagMarks graph as the shared baseline (main env).
    --envrequired for mainOnly case where you push to main env directly.

  3. Plan new features on top

    /tl:plan <target> [initiative=<name>]

    Same args as greenfield. Reuses existing units where match keys hit.

  4. Compose + push implementation

    /tl:compose <target> [--force]
/jetrix:push context              # dev env — in-flight
/jetrix:push implementation
Stage 04 · Quality

Establish the test harness

Set the quality bar dev-validation enforces. Produces qa-output/quality-gates.md — the contract every /dev:build reads.

The repo has just been scaffolded (Stage 05). Decide the test strategy from scratch.

/qa:audit→ /qa:plan→ /qa:setup

  1. Scan repo

    /qa:audit [repo=<path>]
    ArgKindNotes
    repooptionalPath to the product repo. Default: current workspace.

    Read-only. Gap report on unit / integration / e2e / coverage / lint / type-check / CI.

  2. Approve recommendations → plan

    /qa:plan
    ArgKindNotes
    —noneTurns approved recommendations into a plan + draft quality-gates.md.

  3. Implement the harness

    /qa:setup
    ArgKindNotes
    —noneFrameworks, config, CI wiring, fixtures. Flips harness_status: Active when green.

Repo already has tests. Audit finds what's missing without touching what works.

/qa:audit→ /qa:plan→ /qa:setup→ /qa:health

  1. Audit existing harness

    /qa:audit [repo=<path>]

    Same args as greenfield.

  2. Plan the delta

    /qa:plan

  3. Implement missing pieces

    /qa:setup

    Adds missing frameworks, fixtures, CI stages. Never weakens or deletes existing tests.

  4. Health check over time

    /qa:health
    ArgKindNotes
    —noneRe-check for drift. Run monthly or after major refactors.
Stage 05 · Developer

Build features through the loop

Dev-agent runs a state-driven loop with hard guardrails — readiness → impact → plan → implement → validate → repair → self-review → PR handoff.

/dev:bootstrap→ (QA setup)→ /dev:build→ /dev:pr

  1. Bootstrap the codebase

    No code exists yet. Stand up the initial repo with the confirmed stack.

    /dev:bootstrap [repo=<path>]
    ArgKindNotes
    repooptionalWhere to create the repo. Default: current workspace.

    Or use TL scaffold if architecture is already confirmed:

    /tl:scaffold

  2. Set up the QA harness

    Complete Stage 04 before your first /dev:build. Otherwise dev-validation degrades to detected tooling.

  3. Build a feature

    /dev:build [<target>] [initiative=<name>] [repo=<path>] [mode=implement|plan-only]
    ArgKindNotes
    targetoptionalFEAT-id, folder, or slug. Omit → picks next READY_FOR_DEV.
    initiativeoptionalRestrict selection to one initiative's features.
    repooptionalProduct repo to implement in. Default: current workspace.
    modeoptionalimplement (default) or plan-only (stops after dev plan).

    Two automatic checks at startup:

    • MC pre-flight — halts cleanly if MC says the task is blocked. Resolve locally, push, re-run.
    • Drift check — if local is ahead of Jetrix, prompts y (build local) or s (stop, push first).

  4. Handle blockers mid-run

    Dev-agent writes dev/escalation-<n>.md, auto-pushes MC status to blocked. Read the escalation, provide the decision, re-run /dev:build.

  5. Hand off for PR

    /dev:pr <target>
    ArgKindNotes
    targetrequiredFEAT-id, folder, or slug — the feature to prepare handoff for.

    Writes dev/pr-summary.md, moves state to READY_FOR_PR, auto-pushes MC status to devReview.

/dev:build→ /dev:pr
Same commands as greenfield — no /dev:bootstrap (repo exists). Dev-agent uses the reverse-mapped graph to resolve role names → real code files.

  1. Confirm QA harness is Active

    If qa-output/quality-gates.md is harness_status: Active, you're good. Otherwise loop back to Stage 04.

  2. Build a feature

    /dev:build [<target>] [initiative=<name>] [repo=<path>] [mode=implement|plan-only]

    Same args as greenfield.

  3. Re-map if code drifts from graph

    Run periodically. Updates in place, doesn't duplicate.

    /tl:map
/jetrix:push context --env=main

  4. Hand off for PR

    /dev:pr <target>
Stage 06 · Ship

Review, merge, promote

Human reviews the PR, merges to main. GitHub webhook flips MC Task status. If context files changed, the merge agent promotes them dev → main automatically.

Ship is identical for greenfield and brownfield. Same GitHub webhook, same context-merge behavior.

  1. Reviewer reads dev/pr-summary.md

    Purpose, scope, technical approach, affected units, tests run, AC status, risks, follow-ups.

  2. If reviewer requests changes

    /dev:fix-review <target>
    ArgKindNotes
    targetrequiredFEAT-id, folder, or slug — feature with the PR to fix.

    Dev-agent re-enters REVIEW_FIXES — folds actionable comments in, re-validates, refreshes the PR summary.

  3. Merge the PR on GitHub

    Reviewer clicks Merge. GitHub webhook fires to Mission Control.

  4. Automatic post-merge

    • MC Task status → done
    • Context files — if the PR touched context/frontend|backend|database/ files, MC's merge agent LLM-merges dev env → main env automatically
